# 架构设计文档写作规范

OpenClaw（pm-01 子Agent）｜2026-05-30

## 1. 文档定位与适用范围

这份规范用于约束 SEVO、ACO、KIVO、AEO、Claw Design、Exam Sprint 等 OpenClaw 上层插件与应用项目的 `architecture.md` 写法。

它服务两类读者：

- 编码 Agent：看完后能按边界落实现，不靠猜。
- 审计 Agent：看完后能逐章检查实现有没有越界、漏实现、假闭环。

这份规范只覆盖上层产品的系统组织方式，不覆盖 OpenClaw runtime 自身设计。也就是说，`architecture.md` 要写的是“我们的项目如何借 OpenClaw 提供的能力完成业务目标”，不是“OpenClaw 底层怎样实现消息路由和多 Agent runtime”。

适用范围：

- extension / plugin 的注册、权限、输入输出、失败处理
- 流水线状态机、任务看板、session state 等状态管理
- hook 事件消费链路与失败恢复
- prompt-injector 与其他注入机制的职责边界
- 项目之间、模块之间、服务之间的接口咬合面
- doctor、日志、看板、健康检查等可观测性设计

不适用范围：

- OpenClaw runtime / orchestrator 内核设计
- Agent 身份体系与生命周期底层实现
- 消息总线协议、跨 runtime 通信协议
- 分布式 runtime、worker 集群、网关底层调度

## 2. 与 spec / interaction-design 的边界

`architecture.md` 不是产品需求文档，也不是交互稿说明。

边界要写清三件事：

### 2.1 spec 管什么

spec 负责定义：

- 用户是谁
- 用户要完成什么任务
- 为什么需要这个能力
- 功能需求与验收标准
- 体验流与结果要求
- 内容质量、数据真实性、开箱即用等产品门禁

如果一句话在回答“用户想要什么结果”，它就应该写在 spec。

### 2.2 interaction-design 管什么

interaction-design 负责定义：

- 页面/界面有哪些关键区域
- 用户按什么顺序操作
- 每一步看到什么状态、提示、反馈
- 失败时如何感知、如何回退

如果一句话在回答“用户如何操作、看到什么界面反馈”，它就应该写在 interaction-design。

### 2.3 architecture.md 管什么

`architecture.md` 负责定义：

- 哪个模块接住需求，并把它变成可执行流程
- 状态怎么存、谁是唯一真相源、失败如何恢复
- extension / hook / prompt injection 在哪里生效，顺序是什么
- 模块之间怎么交互，输入输出是什么，谁不该承担什么职责
- 怎么观测、怎么诊断、怎么证明流程真的跑通

如果一句话在回答“系统怎样组织起来，才能稳定地产生 spec 要的结果”，它就应该写在 `architecture.md`。

### 2.4 写作约束

架构文档禁止新增 spec 没定义的产品能力。确实需要新增边界时，必须先补 spec，再在架构文档里承接。

## 3. 必须章节列表

下面这些章节是所有上层项目 `architecture.md` 的必写项。每章都要同时满足“写什么”和“质量判据”。

### 3.1 文档定位与范围

要写什么：

- 本文覆盖的项目、模块、运行环境
- 本文明确不覆盖的内容
- 架构目标适用到哪一层

质量判据：

- 读者能判断这份文档能不能直接指导当前项目实现
- 不会把底层 runtime 问题误写进上层项目架构

### 3.2 架构目标与非目标

要写什么：

- 本架构必须保证的系统性质
- 当前明确不解决的问题

优先写这几类目标：

- 流程自动推进
- 状态一致性
- 审计闭环
- 插件边界可控
- Prompt 注入顺序稳定
- 失败可恢复
- 可观测、可诊断

质量判据：

- 每个目标都能在后文章节找到对应机制
- 非目标能拦住“顺手扩功能”

### 3.3 系统上下文

要写什么：

- 项目与 OpenClaw、飞书、GitHub、数据库、文件系统、模型供应商、浏览器、外部 API 的关系
- 每个外部依赖的调用方向、协议、权限、失败影响

质量判据：

- 外部系统不是一团黑盒
- 任意一个依赖挂掉，读者能知道影响哪条流程

### 3.4 核心模块与职责边界

要写什么：

- 模块清单
- 每个模块的职责、输入、输出、依赖、不负责的内容

上层项目至少要覆盖这些边界：

- 入口层
- 状态管理层
- extension / plugin 层
- 事件消费层
- prompt 注入层
- 业务核心层
- 可观测性层

质量判据：

- 每个模块一句话能说清职责
- 没有两个模块同时负责同一件关键事
- “不负责”写得明确，能防止越界实现

### 3.5 插件与扩展机制

要写什么：

- extension 如何注册、发现、加载
- 能力声明放在哪里
- 插件可访问哪些资源，不能访问哪些资源
- 输入输出 schema
- 超时、重试、失败返回
- 权限、密钥、配置项归属
- 升级、禁用、回滚的处理方式

质量判据：

- 编码 Agent 看完后能新增一个插件，不需要猜接入点
- 审计 Agent 能据此判断某个插件是否越权

### 3.6 状态管理与真相源

要写什么：

- 流水线状态、任务状态、session state、文档状态等分别放在哪里
- 哪些状态是文件真相源，哪些是数据库真相源，哪些只是缓存
- 状态枚举、合法迁移、失败迁移、终态
- 幂等、锁、并发约束
- checkpoint / resume 条件

重点必须覆盖：

- 流水线状态机
- 看板状态
- session state
- completion 丢失后的恢复依据

质量判据：

- 任意一个状态字段都能说清 owner
- 任意一次状态变化都能追到触发事件
- 重复事件不会把系统打乱

### 3.7 事件消费与响应链路

要写什么：

- hook 哪些 OpenClaw 事件
- 每个事件触发哪个 handler
- handler 读取什么上下文、写回什么状态、产出什么副作用
- 失败时重试、降级、告警还是人工介入

建议至少写清：

- message:received
- task/completion 类事件
- doctor / healthcheck 相关事件
- watcher / cron 触发的事件

质量判据：

- 拿任意一个事件都能追到后续动作
- handler 失败后不会出现“表面成功、实际没推进”

### 3.8 Prompt 注入链路

要写什么：

- prompt-injector 的职责
- 它与 system prompt、角色 prompt、项目上下文、知识注入、用户消息之间的顺序关系
- 哪一层能注入，哪一层不能改写核心约束
- 注入冲突时谁优先
- 注入失败时系统如何降级

质量判据：

- 读者能画出一次 prompt 组装顺序
- 不会把产品规则、架构规则、临时上下文混成一锅

### 3.9 模块间接口与项目咬合面

要写什么：

- 模块之间传什么对象、什么字段、什么状态
- 项目之间如何交互，比如 SEVO 与 ACO、KIVO、AEO 的咬合面
- 命令接口、事件 payload、文档同步接口、内部 schema
- 错误返回与兼容策略

质量判据：

- 每个接口都能直接落成类型定义或测试 fixture
- 交界面不会出现“大家都以为对方会处理”

### 3.10 运行时关键流程

要写什么：

- 从触发到完成的主流程
- 审计失败后的修复闭环
- 插件调用失败路径
- 状态恢复路径
- 文档真相源与本地备份同步路径

这里的“运行时”指上层产品流程，不是 OpenClaw runtime 内核。

质量判据：

- 编码 Agent 能据此实现 handler
- 审计 Agent 能按流程做端到端核查

### 3.11 可观测性与健康诊断

要写什么：

- 要看哪些日志
- trace 维度如何串起来
- doctor 检查什么
- 看板怎么看
- 健康检查怎么判定正常、警告、阻断
- 用户视角如何闭环验证

重点必须覆盖：

- doctor
- 日志
- 看板
- 健康诊断
- 排障路径

质量判据：

- 出现卡死、假完成、状态不一致时，读者知道先查什么
- 关键结论不依赖记忆，只依赖客观状态源

### 3.12 安全、权限与失败处理

要写什么：

- 密钥和凭据放哪
- 哪些操作必须人工确认
- 文件读写和外发边界
- 外部内容注入的隔离策略
- 失败分类、告警等级、回滚或补偿方式

质量判据：

- 编码 Agent 不会把高风险动作静默自动化
- 审计 Agent 能判断失败是否被正确分级和兜底

### 3.13 验证计划

要写什么：

- 架构层如何验收
- 要跑哪些端到端场景
- 要故意制造哪些失败场景
- 如何验证看板、doctor、日志与真实状态一致

质量判据：

- 不是“理论上可行”，而是“有明确的验证动作和通过标准”

### 3.14 风险与已知限制

要写什么：

- 当前还没解掉的真实限制
- 触发条件
- 影响范围
- 临时降级方式

质量判据：

- 风险写得具体，不写空话
- 读者能据此判断哪些地方不能盲改

## 4. 不需要写的内容

为了避免把架构文档写成大而空的技术杂谈，下面这些内容默认不要写：

### 4.1 OpenClaw runtime 底层设计

不要写：

- runtime / orchestrator 内核怎么实现
- Agent 身份与生命周期底层机制
- 消息路由协议
- 分布式 worker / gateway / runtime 集群设计

原因：这些不是上层产品边界，写进去只会让文档跑偏。

### 4.2 与当前项目无关的通用概念科普

不要写：

- 什么是 Agent
- 什么是 LLM
- 什么是 RAG
- 什么是插件机制

原因：读者不是初学者，文档目标是指导实现与审计。

### 4.3 逐文件解释

不要把 `architecture.md` 写成源码导览，除非某个文件本身就是关键边界定义文件。

### 4.4 未来幻想

不要写还没进入 spec 的能力蓝图，不要用“未来支持”“后续可扩展到”撑篇幅。

### 4.5 修订过程痕迹

不要写：

- 本次新增
- V2/V3
- 修订后
- 来源于某次调研
- 从某文档搬运

交付文档应该像“它本来就是这样”，不是给自己留施工日志。

### 4.6 抽象口号

不要写：

- 高内聚低耦合
- 可扩展可维护
- 强鲁棒性
- 极致体验

除非后面立刻接上可验证的具体约束，否则都是废话。

## 6. 写作质量底线

所有项目的 `architecture.md` 都必须满足下面四条底线：

### 6.1 可实现

编码 Agent 读完后，知道该新增哪个模块、改哪个接口、补哪条状态迁移。

### 6.2 可审计

审计 Agent 读完后，能逐项判断实现是否越界、漏实现、假闭环。

### 6.3 可追溯

关键边界能追溯到 spec、状态源、接口契约、日志字段或验证动作。

### 6.4 可验证

文档里的每个关键机制，都能通过命令、日志、看板、页面操作或测试场景验证，不接受“设计上如此”但没有证据链。
