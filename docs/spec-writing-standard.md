# SEVO Spec 撰写规范

本文档是所有 SEVO 受管项目产品需求规格（product-requirements.md）的结构与质量标准唯一真相源。

## 目录结构（强制顺序）

所有 spec 必须按以下 H2 章节顺序组织，功能需求之前的章节不可缺失：

1. **场景** — 产品在什么情境下被使用（时间、地点、触发条件）
2. **人群** — 谁在用（具体角色、设备、技术背景）
3. **用户故事旅程** — 按场景阶段划分（Stage 1/2/3...），每阶段包含：阶段名称、触发条件、核心动作、阶段产出、转换条件
4. **痛点** — 用户现在怎么解决、哪里痛（要有画面感：具体人、数字、动作、结局）
5. **需求** — 用户要什么（用人话说，不是系统语言）
6. **解决方案** — 包含四个子章节：
   - **产品定位（产品概念）**：一段话说清产品的生态位——面向谁、是什么类别、用什么核心机制、解决什么关键断点、让 Agent 获得什么能力、常被误解成什么。
   - **需求范围**：三段式边界声明——本产品负责什么、可以和谁协同、不负责什么，并显式写出非范围声明。
   - **用户体验流**：每一步用户操作什么、AI 做什么、交互形态是什么。每步标注关联 FR 编号。
   - **功能需求**：FR 列表，每个 FR 必须能追溯到体验流中的某一步
7. **非功能需求**

## 章节质量要求

### 场景
- 必须描述具体情境，不能是抽象分类
- 好：「考前 7 天，学生打开手机想快速过一遍重点」
- 坏：「学习场景」「复习场景」

### 人群
- 必须有具体角色画像，不能只有标签
- 包含：角色名、技术背景、使用设备、核心诉求

### 用户故事旅程
- 按用户心智模型和时间约束划分阶段，不是按系统模块
- 每个阶段必须包含：阶段名称、触发条件、核心动作、阶段产出、转换条件
- 坏：按「上传模块」「练习模块」划分

### 痛点
- 要有画面感：具体人名、数字、动作和结局
- 坏：「认知负担重」「效率低」

### 需求
- 用人话说用户要什么
- 坏：「系统应支持 XX 功能」

### 产品定位
产品定位不是功能罗列、不是技术方案、不是愿景口号，而是一段说清生态位的话。它必须回答六件事：

- 面向谁（目标用户 / 场景）
- 是什么类别的产品
- 通过什么核心机制
- 解决什么关键断点
- 让 Agent 系统获得什么能力
- 常被误解成什么（非范围澄清）

推荐结构：

> [产品名] 是面向 [目标用户 / 场景] 的 [产品类别]。它通过 [核心机制]，解决 [关键断点]，让 Agent 系统获得 [最终能力]。[产品名] 常被误解为 [常见误解]；它的核心价值是 [差异化价值]。

从这个定位展开功能需求。一句「不是 XXX」能挡掉外部读者的错误对标，比多写十个功能点更能说清产品到底占哪个生态位。

### 需求范围
需求范围不是「所有沾边的能力都写进来」，那会让边界无限扩张，也会和兄弟产品职责重叠。它要写成边界声明，回答三件事：本产品负责什么、能和谁协同、不负责什么。

三段式结构：

- 本产品负责 [核心闭环]，包括 [一级范围 1 / 2 / 3]
- 本产品可以与 [其他模块] 协同，但不负责 [非范围事项]
- 当任务进入 [边界条件] 时，应交由 [其他模块] 继续处理

每个一级范围一行，写清这一段负责什么、为什么是核心，不展开成功能清单（那是 FR 的活）。

### 非范围声明
需求范围之后必须有一段显式的非范围声明，单独成段，把本产品「不负责什么」写死。它的作用是挡住边界扩张和兄弟产品撞位，所以要点名最容易被误归进来的能力。

写法：一句话说清不碰哪几类事、这些事归谁，最后落到本产品的边界是什么。

> [产品名] 不负责 [非范围 1]、[非范围 2]、[非范围 3]，这些分别交给 [其他模块]。[产品名] 的边界是：[一句话核心闭环]。

每个 spec 还要补一句输出声明：本产品只负责自己所在环节的闭环，同时向其他模块输出 [结构化结果]。

### 用户体验流
- 人机协同 SOP：每步用户做什么、AI 做什么
- 按用户体验最优设计
- 每步标注关联 FR 编号

### 功能需求
- 每个 FR 必须服务于体验流中某一步
- 体验流中没有对应步骤的 FR = 伪需求
- 体验流中有步骤但没有 FR 支撑 = 功能缺失

### 验收条件（AC）— Solution Spec 规范（强制）

AC 的职责是回答「怎么判断这个 FR 做到了」。每条 AC 必须是可验证的 solution spec，禁止写成 statement spec 的换一种说法。

**必须包含的要素（至少命中 2 项）：**
- 可观测的状态变化（从 A 状态变为 B 状态）
- 具体的数据字段和预期值（哪个字段、什么值、什么格式）
- 明确的边界条件（什么情况下成功、什么情况下失败、什么情况下降级）
- 可执行的验证步骤（做什么操作、看什么结果）
- 时间/性能约束（多久内完成、多少并发下不降级）

**禁止的 AC 写法：**
- ❌「系统应正确显示进度」→ 什么叫正确？哪些字段？什么状态下显示什么？
- ❌「用户体验流畅」→ 流畅的判据是什么？
- ❌「数据应完整」→ 哪些字段必须非空？什么算完整？
- ❌「错误应被妥善处理」→ 什么错误？显示什么？重试几次？

**合格的 AC 示例：**
- ✅「上传完成后，entry.status 从 uploading 变为 processing；页面显示进度百分比（0-100）；超过 5 分钟未完成则 status 变为 timeout，页面显示重试按钮」
- ✅「搜索结果按相关度降序排列；每条结果包含 title、snippet（≤200字）、source_ref；无结果时显示空状态文案而非空白页」
- ✅「LLM 生成的诊断必须包含：错误原因（≤3句）、修复建议（≥1条具体操作）、关联知识点 ID；缺任一项视为生成失败，触发重试」

**审计时的 AC 质量检查：**
- 审计 Agent 读到一条 AC 后，能否不看代码就写出测试用例？能 = 合格，不能 = 不合格
- 如果 AC 需要「理解上下文」才能判断通过与否，说明 AC 写得不够具体

### 内部逻辑自洽
- spec 文档内部各章节之间必须逻辑自洽
- 场景、痛点、需求、解决方案、FR、AC 之间必须形成闭环：痛点能追溯到场景，需求能追溯到痛点，FR 能追溯到需求，AC 能验证 FR
- FR 之间不能有矛盾：不能一个 FR 要求必须走流水线，另一个 FR 又允许跳过流水线
- NFR 不能与 FR 冲突
- 用户体验流中的每一步必须有对应 FR 支撑
- 新增或修改 FR 时，必须检查是否与已有 FR 产生矛盾或重复

## 禁止事项

- 禁止在正文中出现过程性描述（"需要修改""本次调整""更新说明"）
- 禁止用具体学科举例（概率论、数学等），用结构化但学科解耦的措辞
- 禁止「页面级描述」作为验证准则（"页面能打开""列表能显示"不合格）
- 版本历史交给 Git，不写进文档

## 文档真相源规则

所有 SEVO 受管项目的文档以飞书为唯一真相源，本地 md 是 git 备份。

- `product-requirements.md` — PM 产出，产品需求规格
- `architecture.md` — SA 产出，架构设计方案

操作顺序（所有文档统一）：先用 lark-cli docs +update 改飞书 → 再 fetch 到本地备份。禁止先改本地再推飞书。

文档在第一次对应角色介入时创建飞书文档并授权，不提前建空壳。创建后 token 注册到本节下方的项目文档索引中。

## 补充说明：审计为什么必须留在流水线里

审计是流水线里最核心的门禁环节，因为自动化流水线的魂就是用自动化门禁和自动修复来兜住产出质量。审计留在流水线内，审计失败后才能自动回退到 Implement，带着问题清单进入修复，再自动回到 Review 复验，形成 review→fix loop。审计一旦脱离流水线，问题虽然能被发现，但后续修复、复验、放行都要人工重新接回，闭环会当场断掉。流水线的价值就在自动闭环，任何一个环节脱离，闭环都会被打断。
