# SEVO Spec 撰写规范

本文档是所有 SEVO 受管项目产品需求规格（product-requirements.md）的结构与质量标准唯一真相源。

## 目录结构（强制顺序）

所有 spec 必须按以下 H2 顺序组织，功能需求之前的章节不可缺失：

1. **场景** — 具体使用情境，写清时间、地点、触发条件
1. **人群** — 具体角色、设备、技术背景、核心诉求
1. **用户故事旅程** — 按用户心智和时间约束拆 Stage；每阶段包含阶段名称、触发条件、核心动作、阶段产出、转换条件
1. **痛点** — 写清用户现在怎么做、卡在哪里、结果是什么，要有具体人、数字、动作、结局
1. **需求** — 用人话写用户要什么，不写系统口吻
1. **解决方案** — 依次包含产品定位、需求范围、非范围声明、用户体验流、功能需求
1. **非功能需求**

## 开篇与定位

- 产品级 spec 在正文前部必须明确：产品定位、需求范围、非范围声明；缺任一项即边界不清
- 产品定位不是 slogan，至少回答 6 个问题：面向谁、属于什么类别、核心机制是什么、解决什么关键断点、用户最终得到什么、最容易被误解成什么
- 规则必须同时写清：做什么、怎么做、为什么；没有 why 的规则不算完整

## 核心设计原则

所有 SEVO 受管项目的 spec 都必须在功能需求之前写清核心设计原则。原则不是口号，而是后续 FR、AC、设计、实现和审计共同遵循的判断基准。

1. **任意入口全自动走到终局**：从任何阶段进入，都要自动推进到最终验收，不需要人每一步盯着催。Why：入口只处理眼前一步，会让 Agent “修完就停”或“审完就停”，用户看到局部完成，实际交付没有闭环。
1. **任意入口先核实 Spec**：无论从哪个阶段开始，第一步都先确认 spec 存在且覆盖当前任务。Why：Spec 是设计、实现、审计的共同基准；不先核实，后续产物就会各说各话，无法证明满足用户原始需求。
1. **一致性闭环校验**：每个阶段产出必须和 spec 对齐，审计发现问题后形成 review → fix loop 闭环。Why：阶段串联不等于质量闭环；只有偏差能被发现、修复、再验证，错误才不会被一路带到发布。
1. **主动需求澄清**：任何任务执行前，只要存在歧义、多义、范围不明确或目标不清晰，就先澄清；只有任务极其清晰、零歧义时才直接推进。Why：Agent 带着猜测行动，会把入口处的小误解放大成整条流水线返工；先澄清能在成本最低的位置消掉不确定性。

## 章节质量要求

### 场景 / 人群 / 痛点 / 需求

- 场景必须是具体情境，不能写“学习场景”“办公场景”这类抽象分类
- 人群必须有角色画像，不能只有标签
- 痛点必须可感知，不能只写“效率低”“认知负担重”
- 需求必须写用户想完成什么，不能写成“系统应支持”

### 用户故事旅程 / 用户体验流

- 用户故事旅程按用户过程拆分，不按系统模块拆分
- 用户体验流写清每一步里用户做什么、AI 做什么、交互形态是什么
- 体验流每一步必须标注关联 FR 编号；没有流程承接的 FR 是伪需求，有流程但没有 FR 支撑是功能缺失

### 功能需求（FR）

- 每个 FR 必须能追溯到需求和体验流中的某一步
- spec 没覆盖的场景，直接写“本 spec 未覆盖”，不要拿已有 FR 硬凑
- FR 负责定义目标和约束，不预写实现步骤；除非实现路径本身是产品约束，否则不要写“先做 A 再做 B 再做 C”

### 验收条件（AC）

- AC 的职责是回答“怎么判断这个 FR 做到了”；每条 AC 必须是可验证的 solution spec，不能只是 FR 的改写
- 每条 AC 至少命中以下 2 项：可观测状态变化、具体字段和预期值、明确边界条件、可执行验证步骤、时间或性能约束
- 审计者读到 AC 后，必须能不看代码直接写出测试用例；做不到则 AC 不合格
- 禁止页面级 AC，如“页面能打开”“列表能显示”；必须写清对象、状态、字段、阈值、失败或降级表现

### 非功能需求（NFR）

- NFR 每条压成一行带指标，避免冗长叙述
- NFR 不能与 FR 冲突，性能、安全、稳定性约束必须可验证

## 例外、边界与追溯

### 跳过 / 例外条件写法

- FR 涉及“什么时候触发”时，必须同时写清“什么时候不触发”，跳过条件和触发条件同等重要
- 跳过条件必须和触发条件一样精确，使用多项条件共同成立的描述，不能只写一个宽标签放行
- 每个含跳过条件的 FR 必须附至少一个反例：看似该跳过但实际不该跳过的 case，并写清判断原因
- Why：只写正向触发不写例外，会让实现把例外设得过宽，问题常常到 SA 评审才暴露，返工成本更高

### 边界 case 和混合输入

- FR 涉及分类、判定、路由时，必须列出正常输入、边界输入、混合输入三类处理方式
- 正常输入写主路径；边界输入写模糊 case 走哪条路，以及为什么这么判；混合输入写同一指令包含多种意图时的拆分策略
- 混合输入不能被粗暴归到单一路径；必须说明哪些部分分别进入哪个流程，哪些部分需要先澄清
- Why：不列边界 case 的 FR，必然在模糊地带出 bug；分类、判定、路由类功能的主要风险就在灰区

### FR 与设计原则追溯

- 每条 FR 必须标注服务于哪条核心设计原则，至少能追溯到一条原则
- 核心设计原则新增、删除或改写时，必须检查所有关联 FR 是否仍然成立
- 无法追溯到任何原则的 FR，必须额外论证存在必要性；论证不成立则删除或改写
- Why：不追溯原则，审计者无法判断 FR 是必要能力还是随手添加，spec 会逐渐膨胀成不可维护的功能堆积

### 跨项目 FR（双归属）写法

- 跨项目 FR 必须指定主归属和引用归属；主归属写完整定义，引用归属只写一句话说明并附主归属链接
- 同一能力只能有一个主归属，禁止多个项目各自维护完整定义
- 变更时先修改主归属，再同步所有引用归属；引用归属不得自行扩写成另一套定义
- Why：跨项目能力如果各自独立维护，定义必然分叉；主归属负责完整定义，引用归属负责指向，才能让审计和实现始终对齐同一份标准

## 通用化与外部用户视角

- spec 默认面向陌生第三方用户，不能依赖团队内部知识、默认路径、默认账号、默认数据或“大家都知道”的上下文
- 产品目标若包含开箱即用，spec 必须明确安装、初始化和最小可运行路径
- spec 默认面向通用场景，不得把临时样例、当前学科、当前宿主、当前路径写成产品定义
- 涉及路径、配置、环境变量、平台 API 时，必须明确通过配置或 adapter 接入，禁止硬编码

## 压缩与措辞

- 每一行都要回答：这是给读者看的，还是给写作者自己留的；后者一律删
- 保留 FR/AC 编号、域划分结构、Wave 或优先级标记、成功指标；成功指标最多 3 个，每个一行带数字
- AC 已说清的 FR 描述句压成一句或直接删；重复概念只在首次出现时定义；章节间同一内容只保留一处
- 禁止 AI 套话和说明性口头禅
- 禁止过程性描述、来源叙事和修订痕迹；正文只表达当前定义，不复述它是怎么改出来的
- 流程控制类表述直接使用引导、握手、准入校验、路由、提醒、建议、暂停补齐、质量路径未满足等正向措辞
- 文档应读起来像一直就是这样；版本历史和争论过程交给 Git、报告或 ADR，不写进正文

## 一致性与验证

- 场景、痛点、需求、解决方案、FR、AC 之间必须形成闭环：痛点追溯到场景，需求追溯到痛点，FR 追溯到需求和体验流，AC 验证 FR
- FR 之间不能互相矛盾，NFR 不能与 FR 冲突；新增或修改 FR 时必须检查重复、矛盾和边界漂移
- 压缩或改写后必须同时做机械校验和质量校验
- 机械校验：FR 数、AC 数、域数、Wave 或优先级标记完整保留
- 质量校验：是否存在孤儿 FR、孤儿 AC、定位/需求范围/非范围声明三者互相矛盾、是否把实现路径写成产品定义

## 文档真相源规则

- 所有 SEVO 受管项目文档以飞书为唯一真相源，本地 md 是 git 备份
- 标准文档包括：`product-requirements.md`、`architecture.md`、`interaction-design.md`
- 统一操作顺序：先用 `lark-cli docs +update` 更新飞书，再 fetch 到本地备份；禁止先改本地再推飞书

## 设计原则

### 规则类 FR 必须含 Why

规则类 FR 指定义 Agent 行为约束的功能需求。每一条规则类 FR 都必须写清三件事：做什么、怎么判断、为什么创建这条规则。缺少 Why 的规则类 FR 不通过 spec review。

Why 要用一句话说清：如果没有这条规则会发生什么坏事，或这条规则保护什么价值。

LLM 只有理解规则意图，才会在边界场景里做出符合原意的判断。只写动作和判断标准，会让规则变成教条，Agent 容易机械匹配或绕开规则。
