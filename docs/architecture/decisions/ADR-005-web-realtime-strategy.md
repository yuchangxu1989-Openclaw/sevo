# ADR-005-Web: 实时更新方案选择

状态：已采纳 | 2026-04-20

## 上下文

用户侧 Web 层需要把引擎状态变化尽快反馈给项目管理者，覆盖的核心场景包括：
- UFR-01 首页项目健康度和待办数量变化
- UFR-03 待办队列的创建、已回复、已收敛
- UFR-07 异常告警与通知
- UFR-05 质量摘要状态变化

候选方案有三类：
- WebSocket：全双工连接，适合高频双向交互。
- SSE：服务端单向推送，浏览器原生支持事件流。
- Polling：前端定时轮询查询接口。

SEVO 用户侧当前是“低频命令 + 中频状态更新”模式。审批、澄清回复、暂停/恢复等动作都可走同步 HTTP 命令，真正需要实时的是引擎对页面的状态回推。

## 决策

Wave 1 采用 SSE 作为默认实时更新通道，Polling 作为降级和断线补偿方案，WebSocket 暂不启用。

设计要点：
- 事件流承载 `project.updated`、`fr.updated`、`todo.updated`、`notification.created`、`health.changed` 等单向事件。
- 所有命令仍走同步 HTTP + JSON，应答只确认命令已接收；最终状态以事件流或后续查询结果为准。
- SSE 连接失败后自动降级为固定间隔轮询，恢复后可重新切回 SSE。

## 替代方案

| 方案 | 优势 | 放弃原因 |
|------|------|---------|
| WebSocket | 全双工、延迟低、适合协作式编辑 | 当前用户侧没有高频双向流量；连接管理、鉴权、水平扩展复杂度更高 |
| 纯 Polling | 基础设施最简单 | 首页、待办、告警会产生明显延迟；高频轮询浪费资源 |
| 长轮询 | 比普通轮询实时性更好 | 服务端实现和连接管理复杂度接近 SSE，但浏览器侧体验和标准化程度更弱 |

## 后果

- Wave 1 能较低成本满足首页、待办、告警、质量状态的实时刷新需求。
- 前端需要实现 SSE 断线重连和轮询降级逻辑。
- 服务端需要维护事件主题和订阅权限校验，但不必承担 WebSocket 会话管理复杂度。
- 如果未来出现多人协同编辑、页面内聊天或高频双向交互，再评估是否引入 WebSocket。
