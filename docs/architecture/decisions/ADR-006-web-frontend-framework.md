# ADR-006-Web: 前端框架选择

状态：已采纳 | 2026-04-20

## 上下文

SEVO 用户侧 Web 层需要承载项目总览、FR 列表、FR 详情、待办队列、门禁审批、工件预览和通知中心。页面特点是：
- 读多写少，查询聚合重于本地复杂计算。
- 需要 URL 可分享、支持深链跳转到某个项目/FR/待办。
- 需要同时处理首屏加载、局部刷新、SSE 实时更新和文档预览。
- API 契约必须保持框架无关，不能把核心业务逻辑绑死在某个前端状态管理范式上。

候选框架：
- React + Next.js App Router
- Vue + Nuxt
- 纯 SPA（React/Vite）

## 决策

Wave 1 选择 **React + Next.js App Router** 作为 Web 宿主框架,并与 KIVO 保持统一。

采用原因：
- 两个项目共享同一套组件库和页面骨架时,React 组件、布局约定、表单和状态处理可以直接复用,避免 KIVO 与 SEVO 各养一套前端资产。
- Next.js 的页面路由、布局、服务端渲染和数据获取约定适合项目总览、FR 详情、文档预览这类页面型应用。
- 团队技能栈统一在 React + Next.js,可以减少跨项目切换成本,降低维护和招聘培训成本。
- React 生态适合构建 UFR 对应的组件树,如项目卡片、阶段时间线、门禁审批面板、澄清回复面板。
- App Router 便于按页面边界组织 `ProjectDashboardPage`、`ProjectFrBoardPage`、`FrDetailPage` 等组件,同时保留按需客户端交互。
- 与 REST + SSE 契约天然兼容,不要求后端配合专有 RPC 协议。

## 替代方案

| 方案 | 优势 | 放弃原因 |
|------|------|---------|
| Vue + Nuxt | 学习成本低、文件式路由成熟 | 对当前团队和现有组件生态没有明显优势，迁移收益不足 |
| 纯 SPA（React/Vite） | 部署简单，完全前后端分离 | 首屏加载、文档预览、深链落地和页面级组织需要补更多基础设施 |
| 直接在宿主环境嵌入静态 HTML | 实现快 | 难以支撑 FR 详情、待办、通知和权限控制的持续演进 |

## 后果

- SEVO 与 KIVO 可以复用同一套 React 组件库、设计 token、页面骨架和交互约定,减少重复建设。
- 页面结构、路由和预览能力可较快搭起来,适合 MVP 交付。
- 前端实现会默认围绕 React 组件组织,API 契约仍保持框架无关;未来若更换框架,可复用现有后端接口。
- 维护成本下降:构建链、脚手架、测试方案和发布流程可跨项目复用,减少两套前端技术栈并存的长期负担。
- 团队协作成本下降:成员在 KIVO 与 SEVO 间切换时无需切换前端心智模型。
- 需要处理服务端渲染页面与 SSE 客户端订阅的边界,避免重复拉取和水合不一致。
- 若未来需要嵌入到其他宿主 UI 中,可保留 BFF 和 View Model,不必连带重写引擎层。
