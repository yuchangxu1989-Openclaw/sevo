# ADR-003: 门禁采用声明式规则引擎

状态：已采纳 | 2026-04-19

## 上下文

SEVO 有两道关键门禁（Spec Review Gate、Contract Review Gate），未来可能增加更多。门禁逻辑包括工件完整性检查、评审角色分配、多方结论汇总。需要在不修改核心代码的前提下调整门禁行为。

## 决策

门禁检查规则采用声明式配置。每道门禁定义为一组规则条目，包含：必需工件列表、评审角色列表、放行条件（全部通过 / 多数通过）、阻断行为。Gate Engine 读取规则配置执行检查，不硬编码具体门禁逻辑。

## 替代方案

| 方案 | 优势 | 放弃原因 |
|------|------|---------|
| 硬编码门禁逻辑 | 实现快 | 新增门禁或调整规则需要改代码，违反 NFR-5.12 |
| 通用规则引擎（如 Drools） | 表达能力强 | 引入重量级依赖，Wave 1 场景不需要复杂规则表达 |
| 脚本化门禁（每道门禁一个脚本） | 灵活 | 缺乏统一结构，难以做 dry-run 和规则审计 |

## 后果

- 新增门禁只需添加配置条目，核心代码零改动。
- 支持 dry-run 模式，配置变更前可预检。
- Wave 1 规则表达能力有限（条件为工件存在性 + 评审结论），Wave 2 可扩展为条件表达式。
- 两道门禁的差异（单人评审 vs 三方会审）通过评审角色列表和放行条件配置区分，无需分支代码。
