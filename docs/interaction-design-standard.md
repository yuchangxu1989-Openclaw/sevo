# 交互设计文档写作规范

OpenClaw（pm-02 子Agent）2026-05-30

## 1. 文档定位与适用范围

这份文档不是讲产品为什么做，也不是讲技术怎么实现。它只回答一件事：用户在页面里怎么操作，系统每一步怎么反馈，开发该把哪些交互规则做出来。

适用范围：所有需要交付 `interaction-design.md` 的项目与页面，尤其是列表、详情、状态展示、对话、生成式结果、异步任务这几类常见界面。

读者默认是编码 Agent。写法必须具体到页面分区、字段、按钮文案、状态机、异常处理，不能写空话。

## 2. 与 spec / architecture 的边界

### spec 负责什么

- 用户是谁，为什么需要这个功能
- 功能范围是什么
- 验收标准是什么
- 体验流从哪里开始，到哪里算完成

### interaction-design 负责什么

- 页面分成哪些区
- 用户一步步怎么操作
- 系统一步步怎么反馈
- 每个按钮、字段、状态、提示具体怎么定义

### architecture 负责什么

- 用哪些模块、服务、数据流支撑这些交互成立
- 状态如何产生、同步、持久化
- 流式输出、异步任务、通知、权限如何实现

一句话分界：spec 定义做什么，interaction-design 定义怎么用，architecture 定义怎么撑起来。

## 3. 必写章节列表

默认精简为 9 个必写章节。大多数页面写完这 9 个，就足够让编码 Agent 直接实现。

### 3.1 页面 / 流程概览

**要写什么**

- 页面名或流程名
- 目标用户
- 使用时机
- 页面目标
- 成功结果
- 上游入口
- 下游去向

**质量判据**

- 读完后能立刻说清：用户为什么会来这里，做完什么算完成
- 不能只写“这是任务页面”“这是详情页”这种空描述

### 3.2 交互模式声明

**要写什么**

- 当前页面是对话式、表单式还是混合式
- 主输入方式是什么
- 辅助输入方式是什么
- 为什么采用这种模式

**质量判据**

- 编码 Agent 能直接判断页面骨架
- 避免把本该结构化输入的页面做成纯聊天，也避免把需要追问修正的页面做死成纯表单

### 3.3 页面分区与信息结构

**要写什么**

- 页面有哪些区域
- 每个区域展示什么
- 每个区域承载什么动作
- 区域之间怎么联动

**质量判据**

- 读完能画出页面骨架
- 区域边界清楚，不能只写“上面是信息，下面是结果”

### 3.4 核心操作流

**要写什么**

- 用户每一步做什么
- 系统立即反馈什么
- 后台开始什么处理
- 成功后页面怎么变化
- 失败后留在什么状态、给什么恢复动作

**质量判据**

- 至少覆盖主路径和 1 到 2 条高频分支
- 每一步都要同时写用户动作和系统反馈

### 3.5 动作定义

**要写什么**

- 每个按钮、菜单、输入框、卡片动作的名称
- 所在位置
- 触发条件
- 禁用条件
- 点击后的即时反馈
- 成功结果
- 失败结果
- 是否可撤销

**质量判据**

- 编码 Agent 不需要猜按钮叫什么、点了会怎样
- 禁止出现“用户可以编辑”“可以重新生成”这种没有规则的描述

### 3.6 字段与内容展示规则

**要写什么**

- 每个区域显示哪些字段
- 字段含义和来源
- 展示格式
- 是否必显
- 空值怎么显示
- 超长怎么处理

**质量判据**

- 能直接映射成前端 schema 或 props
- 不能只写“显示任务信息”“显示结果摘要”

### 3.7 页面状态机

**要写什么**至少覆盖这些状态：

- 初始态
- 加载态
- 空态
- 错误态
- 处理中
- 已完成
- 超时 / 中断

每个状态都要写：

- 触发条件
- 页面展示
- 用户可做动作

**质量判据**

- 不能只有 happy path
- 用户在任何关键状态下都知道系统现在发生了什么、下一步能做什么

### 3.8 AI 特有反馈规则

**要写什么**

- 哪些内容是 AI 生成，哪些是系统确定值
- AI 结果如何标识
- 基于什么输入生成
- 哪里存在不确定性，如何提示用户复核
- 如何重试、修正、继续生成
- 覆盖旧内容还是保留旧内容

**质量判据**

- 用户不会把 AI 猜测误当成确定事实
- 编码 Agent 知道哪里必须加“AI 生成”标识和恢复动作

### 3.9 长任务与异步可见性

**要写什么**

- 任务阶段列表
- 列表页怎么显示进度
- 详情页怎么显示当前阶段与历史记录
- 能不能离开页面
- 离开后回来怎么看续跑状态
- 完成通知怎么做
- 失败恢复入口在哪里

**质量判据**

- 异步任务不会“消失”
- 用户离开页面再回来，仍然知道任务跑到哪了、失败在哪、下一步怎么补救

## 4. Agent 产品必须额外写清的四件事

### 4.1 生成过程可见

不要只写一个 loading。要明确：

- 请求已收到的反馈
- 阶段性进度文案
- 是否有流式输出
- 中途能不能取消
- 卡住多久后进入超时或异常提示

### 4.2 不确定性可见

要明确：

- 哪些内容是 AI 生成
- 基于哪些输入生成
- 哪些结论需要用户复核
- 用户如何重试、修正、缩小范围

### 4.3 异步任务可恢复

要明确：

- 后台继续跑时的展示规则
- 刷新页面后的恢复规则
- 从列表进入详情时能看到哪些历史状态
- 完成和失败的通知方式
- 失败后是否支持重试、续跑、回看失败原因

### 4.4 混合交互模式要声明分工

如果一个页面同时有表单和对话，必须写清：

- 哪部分信息必须结构化填写
- 哪部分内容允许自然语言补充
- 表单提交后是否进入对话修正
- 对话修正后是否反写结构化结果

## 5. 按需章节

只有页面足够复杂，或确实影响实现时，才补这些章节：

### 5.1 边界场景

适合：存在大量高频坏路径的页面。

至少优先写：

- 输入太短或太长
- 重复提交
- 生成到一半中断
- 历史结果和当前输入不一致
- 权限不足
- 多端切换后的状态保持

### 5.2 响应式 / 多端差异

只在桌面端和移动端的交互真的不同的时候写。

重点写：

- 哪些区域会折叠
- 哪些动作会从按钮变成菜单
- 长列表、长日志、小屏输入区怎么处理

### 5.3 对接假设

当交互依赖明确状态字段时再写。

重点写：

- 页面依赖的核心实体
- 最少需要哪些状态字段
- 前端判断各状态依赖什么标记位
- 页面刷新是轮询、推送还是手动刷新

### 5.4 开发验收清单

适合：页面复杂、容易漏状态、需要直接给审计和开发验收使用。

至少覆盖：

- 主流程可走通
- 按钮文案与文档一致
- loading / empty / error / content 都可触发
- AI 输出标识完整
- 长任务离开页面再回来仍可追踪

## 6. 不需要写的内容

交互文档里不要写这些：

- 配色、圆角、阴影、间距等视觉规范
- 白底黑字之外的视觉讨论
- Figma 图层、视觉走查备注、像素标注
- 前端技术选型、组件库、状态管理实现
- 后端接口细节、数据库设计
- “希望感觉智能”“要丝滑一些”这类空话
- 低概率异常的大段罗列

这份文档服务的是实现，不是展示设计过程。

## 7. 质量门槛

一份合格的 interaction-design.md，至少要满足下面四条：

### 7.1 动作够具体

不是“支持重新生成”，而是“按钮文案叫‘重新生成’，点击后立刻进入生成中状态，按钮禁用，原结果保留直到新结果成功返回”。

### 7.2 状态够完整

不是只有正常态。加载、空、错、处理中、部分完成、超时、中断都要定义。

### 7.3 字段够落地

不是“展示任务信息”，而是“展示任务名、发起时间、当前阶段、失败原因摘要、最近更新时间”。

### 7.4 坏路径够真实

不是教科书式异常清单，而是真实用户最常撞到的问题和恢复方式。

最后只问一句：编码 Agent 能不能不脑补就把页面做出来。能，就是合格；不能，就继续补。
